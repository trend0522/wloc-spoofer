# 層級 2 真機驗證清單（P8-e 待執行）

狀態：**自動化測試通過（44/44，含 dist 產物 vm 級端對端），待真機驗證。**
在真機驗證通過前，功能分支 `feature/route-sim-level2` 不合併 main——
合併 main 即等於向所有裝置使用者发布新模組產物，必須由真機證據放行。

## 產物與安裝檔相容性（靜態已驗證）

- `modules/*`（安裝規則檔）**零改動**：script-path 指向 repo main 分支 raw URL、
  `argument` 深圳預設值未動 → 合併後代理工具自動取用新 dist，使用者不需要重安裝。
- 舊讀端 × 新寫端：未更新模組的使用者，其舊 wloc.js 完全不認 `wloc_route` key → 零副作用。
- 新讀端 × 舊狀態：無 `wloc_route` 時 `Ze()` 與基線 `ZeBase()` 全等（測試案例1 逐欄斷言）。
- 建置可重現：`npm run build:dist`；漂移測試保證 dist/ = dist-base/ + modules-src/ 即時重構。
- 回滾：git revert dist 的 commit → raw URL 立即回復舊產物；裝置端另有逃生閂——
  網頁「停止並清除」（route-clear）即刻回到單點模式，不需要碰模組。

## 真機最小操作步驟（iPhone + Stash 或 Surge）

1. 裝模組：從選點頁安裝現有 WLOC 模組（安裝檔不用改）。
2. 先用既有單點功能做一次基準：選點→儲存到裝置→地圖 App 顯示偽造點（證明 MITM 生效）。
3. 切到本分支部署的選點頁（合併後即正式 URL），規劃一條步行路線（如車站→101）。
4. 按「開始定位模擬」→ 必須顯示「✓ 已寫入裝置…」；若顯示失敗訊息=通道不通，記錄訊息。
5. 開 Apple 地圖（或依賴 gs-loc 網路定位的 App），觀察定位點：
   - **沿路線逐次移動**（非連續滑動，跳點粒度=App 請求節律，這是設計行爲）
   - 記錄两次明顯跳點之間大約幾秒 → 這是本方案的实际更新粒度，回報用。
6. 網頁按「暫停裝置模擬」→ App 位置應停住；「繼續」→ 從暫停處恢復、無跳躍。
7. 等抵達終點（可先調高速度倍率）→ 位置應停在終點不再動。
8. 按「停止並清除」→ 回到步驟 2 的單點行爲（或透傳）。**必須確認單點功能完好**。
9. 重新整理網頁 → 「開始定位模擬」區應自動顯示進行中的模擬狀態（route-status 探測）。
10. 背景/鎖屏測試：模擬中把 App 切背景 60 秒再回前台 → 位置應跳到「此刻該在」的點
    （事件式插值的預期行爲），確認無 crash、無卡在舊點。
11. （容量邊界，可選）一條 >200km 路線啟動模擬，確認各平台 persistentStore 不拒絕
    （shape ≤3KB 降採樣保護）；若某平台失敗，記錄平台+訊息。
12. 若裝置端有 wloc_settings 舊值，確認 route-clear 後舊值原樣可用（測試案例6已覆蓋
    邏輯層，真機再確認一次）。

## 無法在本機驗證、只能靠真機數據的項目

- gs-loc 請求節律（决定體驗）；App 端定位快取造成的顯示滞后。
- 各平台 persistentStore 值長度上限實際值。
- 純 GPS 場景不受影響之確認（預期本模組完全不介入，與現行行爲一致）。
- QX（$prefs）通道的 route-* 寫入（邏輯共用同一 adapter 代碼路徑，但 $prefs 與
  persistentStore 的序列化語意細節需實測）。
